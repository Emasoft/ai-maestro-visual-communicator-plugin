# publish-gate-and-release-invariants

See also [[test-suite-flakes-are-host-load]] — the G4 browser gate is the one
release gate that fails for reasons that have nothing to do with the release.


^ATOM-K4DO-E7XL [desc:"every release needs the {name}--v{version} twin or dependents cannot resolve it", keywords: no_git_tag_satisfying plugin_uninstallable dependency_resolver_tag double_hyphen_tag plugin-name--v_version, ocd: 2026-08-08, lmd: 2026-08-08]

Every amvcp release must carry TWO refs: `v{version}` and `{plugin-name}--v{version}` (DOUBLE hyphen). Since Claude Code 2.1.110 a version-constrained plugin dependency resolves by listing this repo tags, keeping ONLY the `{name}--v{version}` form and taking the highest that satisfies the range; the plain `v{version}` tag is ignored entirely, so a repo full of tags still reports "no git tag satisfying <range>". amvcp shipped 6 releases with ZERO resolver tags and nobody noticed, because the failure is silent from BOTH sides: nothing breaks here, and an already-installed dependent keeps working, so it only surfaces the first time someone new installs. scripts/publish.py now emits both in one --atomic push (_release_tags) and backfills historical releases (_push_resolver_backfill) so a future ^1.3.0 resolves 1.3.6 rather than nothing. [^1]


^ATOM-DSDG-XGM9 [desc:"the tracked pre-push hook refuses publish.py's own release push: HEAD is classified as neither branch nor tag, so branch+tags is misread as tag-only", keywords: tag_name_does_not_match_plugin_version push_rejected_after_every_gate_passed pre-push_hook_blocks_the_resolver_tag publish_green_but_push_fails failed_to_push_some_refs refs/heads_HEAD_not_classified_as_a_branch tag_only_push_misfires release_blocked_by_our_own_guard, type: reference, ocd: 2026-08-11, lmd: 2026-08-11]

The tracked `git-hooks/pre-push` (live via `core.hooksPath=git-hooks`) refuses amvcp's own release push, and TWO defects compound to do it. (1) `_classify_push_refs()` counts a ref as a branch only when LOCAL_REF starts with `refs/heads/`, but publish.py pushes `HEAD` — which matches neither `refs/heads/` nor `refs/tags/` and is silently dropped from BOTH lists. `branch_refs` is therefore empty and `tag_only_push = bool(tag_refs) and not branch_refs` evaluates TRUE for a push that is plainly branch+tags, running a guard documented as tag-only-push-scoped. (2) That guard's `expected_tag` is hardcoded to `f"v{local_version}"`, so the `{name}--v{version}` resolver twin publish.py itself mints is reported as mismatched. Measured 2026-08-11 on v1.5.0: ruff PASS, CPV --strict 0/0/0/0, 454/454 tests, bump, changelog, commit and both tags all succeeded, then `BLOCKED: Tag name does not match plugin version!`. The guard can fire ONLY when `branch_refs` is empty, so its firing is itself the proof of defect (1). [^2] [^3]

## Notes and lessons learned

[^1]: [id:ATOM-64OS-3Z08, status:valid, keywords:"changelog_only_has_one_release CHANGELOG.md_overwritten git-cliff_unreleased history_disappeared release_notes_missing", ocd:2026-08-08, lmd:2026-08-08] DO NOT pass `--unreleased` to git-cliff alongside `--output`, BECAUSE `--unreleased` scopes the render to not-yet-released commits and `--output` overwrites, so every publish leaves a CHANGELOG.md containing ONLY the release just made — amvcp had 6 tagged releases and 1 section, and the same defect was measured fleet-wide (one repo: 1 section against 381 releases). DO render the full history (`git-cliff --bump --tag <v> --output`), and note this class of bug survives indefinitely because the source of truth (the commit log) is undamaged, so every automated gate stays green while only the artifact a human reads is destroyed.
[^2]: [id:ATOM-3YZZ-0KZ2, status:valid, desc:"publish.py's own failure hint misdirects; the real push error is at the TOP of a redirected log, not beside the git push line", keywords:"publish_says_fix_the_network_auth_issue_but_auth_is_fine push_error_missing_from_the_log error_appears_at_the_top_of_the_log_not_next_to_the_command capture_output_False_unbuffered_stderr_ordering ls-remote_works_but_push_fails", ocd:2026-08-11, lmd:2026-08-11] DO NOT believe publish.py's "remote push failed — fix the network/auth issue" hint, or conclude the error was not logged because it is absent next to the `$ git push` line, BECAUSE `_git_push` runs with `capture_output=False`, so git's UNBUFFERED stderr lands near the TOP of a redirected log while publish.py's own Python-BUFFERED prints land at the bottom — the real reason is in the file, just not where you look. DO grep the WHOLE log for `error:`/`BLOCKED`/`fatal:` first, and prove or kill the network/auth theory independently with read-only probes (`git ls-remote`, `gh auth status`) before acting on the hint.
[^3]: [id:ATOM-NFFL-KYU9, status:valid, desc:"adding a new tag shape to the release pipeline requires teaching the push guard about it in the same change", keywords:"added_a_resolver_tag_and_the_release_stopped_pushing guard_rejects_a_tag_the_pipeline_itself_mints new_tag_format_breaks_the_pre-push_check release_path_drift_between_publish.py_and_the_hook", ocd:2026-08-11, lmd:2026-08-11] DO NOT add a new tag shape to the release pipeline (the `{name}--v{version}` resolver twin) without teaching every guard on the push path about it IN THE SAME CHANGE, BECAUSE publish.py and `git-hooks/pre-push` validate the same release independently, so the mint side shipped while the check side kept a hardcoded `v{version}` and blocked the first release that used the new shape. DO grep the push path for tag-name assumptions whenever the tag set changes, and remember the failure surfaces only at the very END of a long green pipeline, after tests and tags have already run.
