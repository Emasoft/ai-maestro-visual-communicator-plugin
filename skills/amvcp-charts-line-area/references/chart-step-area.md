A line/area chart with ORTHOGONAL stepping instead of Catmull-Rom smoothing.
Each segment is a horizontal hop to the next x, then a vertical jump to
the new y — exactly the right shape for a value that JUMPS discretely
between measurements.

## When to choose step-area

Use `step-area` when:

- The metric is a STATE (current balance, current temperature setting, active subscription count) that holds steady between measurements and jumps at discrete events.
- Smoothing between points would IMPLY interpolation that does not exist (a balance of $4500 at 09:00 and $4800 at 10:00 means $4500 the whole time then jumped to $4800; it does not mean a linear ramp).
- The reader should perceive the DURATION of each plateau (the horizontal step length encodes time-at-value).

Pick `line` or `area` when smooth interpolation between points is
meaningful (continuous measurement).
Pick `bar` when the x-axis is categorical.

{

  "subtitle": "One large withdrawal Tuesday",
  "series": [{ "label": "USD", "data": [

Same shape as `line` / `area`. The renderer uses a STEP path instead of a
smooth curve.

## What the runtime emits

```html
<svg class="ve-chart-svg" …>
  <defs>
    <linearGradient id="ve-chart-N-fill" …>…</linearGradient>
  </defs>
  <g class="ve-chart-gridlines">…</g>
  <!-- step area: path is M x0 y0  H x1  V y1  H x2  V y2  …  L xn yBase  L x0 yBase  Z -->
  <path class="ve-chart-area" d="M… H… V… …" fill="url(#…)"/>
  <!-- the step line on top: same M H V H V chain but not closed. -->
  <path class="ve-chart-line" d="M… H… V… …" fill="none" stroke="…"/>
  <g class="ve-chart-points">
    <circle class="ve-chart-point" cx="…" cy="…" r="4" …/>
    …
  </g>
</svg>
```

The step path is generated by `stepPath(points)`:

```js
function stepPath(points) {
  // M x0 y0  H x1 V y1  H x2 V y2  …
  // Each segment: horizontal to next x, then vertical to next y.
  return 'M' + points[0].x + ' ' + points[0].y + ' …';
}
```

## Lib functions called

`renderSvgLine(spec, 'step-area', fig)` — branches on `isStep`:

- `topPath = stepPath(pts)` (instead of `catmullRom(pts)`).
- Area path: `stepPath(pts) + ' L … Z'` (closed to baseline).
- Line path: `stepPath(pts)` (open).
- Gradient defs same as `area`.
- Point circles + `markPoint` same as `line`.
- Draw-on entry animation: `getTotalLength()` + `stroke-dashoffset` works on the step path too (the path is just an alternate `d` attribute).

## Step-area vs alternatives

| Story | Best chart | Why |
|---|---|---|
| Continuous smooth measurement (DAU, latency over time) | `area` | Smooth interpolation matches the data semantics. |
| Continuous measurement, line only (no fill) | `line` | Lower visual ink. |
| Discrete state holds steady until an event (balance, tier, count) | `step-area` | Steps match the "stays this value until …" semantics. |
| Discrete state, no fill | (no built-in type — use `step-area` and CSS-hide the area) | The runtime always paints the gradient when type is `step-area`. |
| Discrete event count per period (commits per day) | `bar` | Bar discretness matches per-bucket counts. |

The step-area is specifically for STATE OVER TIME — the value
HOLDS between measurements and JUMPS at events. Don't use it for
per-period counts (which are bar-shaped, not state-shaped).

## Step direction — HV vs VH

The renderer uses the HV step pattern (Horizontal-then-Vertical from
each point):

```
M x0 y0  H x1  V y1  H x2  V y2  …
```

This means the value HOLDS at the OLD y until reaching the NEW x, then
JUMPS to the NEW y. The old value extends RIGHT until the next
measurement; the jump happens AT the measurement instant.

The alternative VH step pattern (Vertical-then-Horizontal) would jump
to the new y AT the old x, then hold. The runtime uses HV consistently
— most "state holds until next reading" semantics match HV. If you
need VH, you'd need to pre-process the data (insert duplicate points
just before each transition).

## Reading a step-area chart

The plateau LENGTH encodes DURATION at the value. A wide plateau means
"this state held for a long time"; a narrow plateau means "the state
flipped quickly". The eye reads the visual exactly as the data is
intended.

The step VERTICAL RISE encodes the MAGNITUDE OF THE CHANGE. Tall
vertical steps signal big state shifts; short vertical steps signal
incremental changes.

## Anti-patterns

- **Smoothing implied by step-area.** The step shape IS the meaning. If you smooth it in post, you destroy the "values are discrete states" signal.
- **Step-area for continuous data.** Use `line` or `area`. A daily-measured cumulative count is more honestly shown as smooth.
- **Step-area with 2 points.** Becomes a single L-shape — not informative. Use `bar` or a `metric-cards` tile.
- **Negative y values.** Like `area`, the path closes to `yBase` (bottom of plot), not to y=0. Don't use step-area for signed data.
- **Mixing step-area with bar in the same dashboard.** Two visual languages for what looks like similar data (step-area discrete states, bar discrete counts) confuses readers. Pick one and stay consistent across the page.
- **Step-area for stochastic processes.** A genuinely random walk with no flat plateaus shows up as a fence of equal-width steps — the "state holds" semantics aren't real. Use `line` to be honest.

## Visual verification

Verify in `skills/amvcp-self-debug-rules/SKILL.md`: step corners are crisp
(no smoothing artifacts at corners), draw-on animation respects
`prefers-reduced-motion`, gradient fill is consistent with the `area`
chart's gradient (same `--vc-color-accent` stops), plateau widths
proportional to time durations (not all equal — that would imply uniform
spacing in time).
