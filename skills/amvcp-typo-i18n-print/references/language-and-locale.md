Typography is *language-aware* — the browser uses the document's
language declaration to pick hyphenation dictionaries, word-break
rules, quotation-mark glyphs, and rendering hints. If the language
is missing or wrong, every language-dependent typography feature
silently fails. The typography skill enforces a single rule:
`<html lang="…">` MUST be set on every page.

This reference describes the language declaration contract — what to
set, where, and which typography features depend on it.

## What it is

HTML has TWO language-declaration attributes:

| Attribute | Where | Scope |
|---|---|---|
| `<html lang="en">` | One per document | The default language of all content |
| `<p lang="fr">…</p>` | Any element | Overrides the document language for this element |

The `lang` value is a BCP 47 language tag:

| Tag | Meaning |
|---|---|
| `en` | English (any region) |
| `en-US` | American English |
| `en-GB` | British English |
| `fr` | French (any region) |
| `fr-FR` | French (France) |
| `de` | German |
| `ja` | Japanese |
| `zh-Hans` | Chinese, simplified script |
| `zh-Hant` | Chinese, traditional script |
| `ar` | Arabic |
| `he` | Hebrew |

Use a 2-letter language code by default; add a region (`en-US`,
`en-GB`) only when the regional variant matters (typically for
spelling-aware features like browser spellcheck).

## The contract

The typography skill does NOT ship a CSS rule for `lang` — it cannot;
language is declared in HTML, not CSS. The contract is *editorial*:

```html
<!DOCTYPE html>
<html lang="en">
  <head>…</head>
  <body>
    <!-- All content here is English by default. -->
    <p>Body text in English.</p>

    <!-- A French quotation overrides the language. -->
    <p>The phrase <q lang="fr">je ne sais quoi</q> means …</p>

    <!-- A Japanese name overrides. -->
    <p>The artist <span lang="ja">大友克洋</span> directed Akira.</p>
  </body>
</html>
```

The typography skill's specimen page sets `<html lang="en">`. Every
DESIGN.md-themed page generated by the runtime should do the same;
the language tag is part of the runtime's HTML scaffold, not the
typography layer's CSS.

## Which typography features depend on language

### Hyphenation (`hyphens: auto`)

The browser uses the document language to pick the hyphenation
dictionary. Without `<html lang>`, hyphenation either:

- Uses the user's BROWSER LOCALE (which mismatches the content), or
- Uses no dictionary at all (no hyphens applied).

Both are wrong. ALWAYS set the language.

See [hyphenation-and-justification.md](../../amvcp-typo-microtype/references/hyphenation-and-justification.md).

### Quotation marks (`<q>` element)

The HTML `<q>` element renders with the LANGUAGE-APPROPRIATE quotation
marks:

| Language | Open quote | Close quote |
|---|---|---|
| English (en) | " | " |
| French (fr) | « | » |
| German (de) | „ | " |
| Japanese (ja) | 「 | 」 |
| Spanish (es) | « | » or " " |

The CSS `quotes` property declares the per-language quote pairs, but
modern browsers ship sensible defaults — just set `lang` correctly
and `<q>` renders with the right glyphs.

### Word-break rules

Different languages break lines at different points:

- English: break at spaces, hyphens, slashes (sometimes).
- Chinese / Japanese: break between any two characters (no inter-word
  spaces).
- Thai: break at language-aware syllable boundaries (no inter-word
  spaces, but break rules exist).

The browser picks the right break engine based on `lang`. Without it,
defaults may produce wrong breaks (mid-character breaks in CJK,
broken-word lines in English).

### Spellcheck

Most browsers use `<html lang>` to pick the spellcheck dictionary for
`<textarea>` and `contenteditable` elements. The typography skill
doesn't *render* spellcheck (the browser draws the squiggly underlines
itself), but the user-experience contract requires the right language
for spellcheck to be useful.

### Sorting and number formatting

JavaScript's `Intl.Collator`, `Intl.NumberFormat`, `Intl.DateTimeFormat`
all read the document language. If a page renders a sorted list or
a formatted number, the `lang` attribute is what makes it correct.

The typography skill doesn't directly format numbers (that's the
charts / tables skill's job), but the `lang` setting cascades to
those.

### Voice / screen reader

A screen reader changes its TTS engine to match the `lang` attribute.
A French paragraph announced with an English engine sounds *wrong*
(every word mispronounced). For mixed-language content, the per-
element `lang` override switches the engine mid-sentence.

This is the single most-impactful accessibility win from correct
language declaration.

## Scaffold — mixed-language content

```html
<!DOCTYPE html>
<html lang="en">
<body>
  <article>
    <p>The phrase <q lang="fr">je ne sais quoi</q> originates in
       18th-century French philosophy.</p>

    <p>The German word <span lang="de">Schadenfreude</span>
       describes pleasure at another's misfortune; the Japanese
       word <span lang="ja">物の哀れ</span> (mono no aware)
       describes the bittersweet awareness of impermanence.</p>

    <blockquote lang="es">
      <p>El mundo es un pañuelo.</p>
      <cite>— Spanish proverb</cite>
    </blockquote>
  </article>
</body>
</html>
```

Each foreign-language phrase / blockquote is tagged. The hyphenation
dictionary, quotation marks, and screen-reader engine all switch at
the boundary.

## The `dir` attribute — right-to-left scripts

For right-to-left (RTL) scripts — Arabic, Hebrew, Persian — the
direction is set with `dir="rtl"`:

```html
<html lang="ar" dir="rtl">
<body>
  <p>هذا نص باللغة العربية.</p>
</body>
</html>
```

The whole page renders right-to-left: text flows R-to-L; the
scrollbar moves to the left; lists indent from the right; the cursor
in input fields starts at the right.

The typography skill's CSS contract is INDEPENDENT of `dir` — sizes,
weights, fonts, leading all apply identically in LTR and RTL. The
runtime's layout layer handles flex/grid mirroring per `dir`.

For mixed-direction content (an RTL phrase inside an LTR document):

```html
<p>The word <span lang="ar" dir="rtl">سلام</span> means "peace".</p>
```

The `<span>` with `dir="rtl"` flows the Arabic text R-to-L inside the
LTR paragraph. The browser handles the bidirectional algorithm
automatically.

## CJK fonts and `lang="zh-Hans"` / `"zh-Hant"` / `"ja"` / `"ko"`

For CJK languages, the `lang` attribute determines:

- Which CJK font the browser picks (when the font-stack includes
  generic CJK families like `"Noto Sans CJK"` — the JP/SC/TC variant
  is picked per `lang`).
- The word-break rules (`zh` and `ja` break differently from `ko`).
- The horizontal vs vertical writing direction (`writing-mode:
  vertical-rl` for traditional Chinese, controlled by CSS but cued
  by `lang`).

The typography skill defers CJK typography to DT-25 (in
`design-tokens`); the language declaration is the prerequisite that
makes DT-25's CJK contract correct.

## Why we don't use `<meta http-equiv="Content-Language">`

The deprecated `<meta http-equiv="Content-Language">` is sometimes
seen in legacy HTML. It is NOT a substitute for `<html lang>`:

- Browsers don't use it for hyphenation.
- Screen readers don't use it for TTS.
- CSS `:lang()` selectors don't read it.

ALWAYS use `<html lang>`, never the `<meta>` form.

## The runtime's language declaration

The runtime's HTML scaffold (`amvcp-runtime.js`'s page generator) sets
`<html lang="en">` by default. The DESIGN.md frontmatter can override
via a `meta.lang` key (extending the engine schema):

```yaml
meta:
  lang: fr
```

This is the integration pass; the typography skill ships the
*editorial* expectation (every page MUST set `lang`); the runtime
ships the *mechanism*.

## Tokens consumed / extended

- **Consumes:** nothing.
- **Extends:** `meta.lang` (engine schema addition, integration
  pass) — drives the runtime's `<html lang="…">` emission.

## Light + dark — orthogonal

Language affects rendering, not colour. The contract is theme-correct
trivially.

## Selection-contract conformance

A `<span lang="fr">` inside a paragraph is INLINE — not a typography
atom. The parent paragraph atom owns the decision-mini-pill.

The `markTypographyAtoms` walker does not look at `lang` — language
is metadata, not visual shape.

## The `:lang()` CSS selector

CSS provides a `:lang(xx)` pseudo-class to style content per-language:

```css
:lang(fr) {
  font-family: var(--vc-font-body-fr, var(--vc-font-body, inherit));
}
:lang(ja) {
  font-family: var(--vc-font-body-ja, var(--vc-font-body, inherit));
  line-height: 1.8;        /* CJK looser leading */
  letter-spacing: 0.05em;  /* CJK tracking */
}
```

This is the canonical way to apply per-language typography overrides
WITHOUT writing per-element classes. The `:lang()` selector matches
any element with a matching `lang` attribute (or inheriting one from
an ancestor).

The typography skill does NOT ship `:lang()` rules for non-English
languages by default — DT-25 in `design-tokens` owns the CJK CSS,
and per-language overrides are page-local decisions. The `:lang()`
pattern is documented here so the agent knows the canonical mechanism.

## When NOT to set `lang`

`lang` should be set on EVERY page. There is no "when not to". The
question is *which value*:

- Unknown language → use `lang="und"` (the BCP-47 "undetermined"
  code). Better than no `lang` (the browser knows to skip
  language-dependent features).
- Mixed-language page with no dominant language → use the **majority**
  language at the document level, and per-element overrides for the
  minority.
- Auto-generated content where the language varies → set `lang` from
  the source language; the runtime is responsible for setting it at
  generation time.

## Verification

Per `skills/amvcp-self-debug-rules/SKILL.md`:

1. Confirm the page has `<html lang="…">`. Open the rendered HTML;
   inspect the root element.
2. Test hyphenation: set `<html lang="en">`, render `.vc-type-justify`
   prose at narrow width, confirm hyphens appear at end-of-line.
   Repeat with `<html lang="de">` (German has different break rules);
   confirm different hyphenation pattern.
3. Test `<q>` element: render `<q>quoted text</q>` in three pages
   with `lang="en"`, `lang="fr"`, `lang="de"`; confirm the
   quotation marks differ per language.
4. Test screen reader (manual): use VoiceOver / NVDA / JAWS; load
   a page with mixed `lang` annotations; confirm the engine switches
   pronunciation at each tagged span.
