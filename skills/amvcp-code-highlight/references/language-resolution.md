# Sub-technique A7 — Language resolution + the 17-alias map

How the tokenizer resolves a `<pre>`'s language id from author markup,
the full alias map, and the canonical "null = no highlighting" failure
mode. From `scripts/amvcp-code-highlight.js → detectLanguage` +
`normalizeLang`.

## A7.1 The resolution rule

The tokenizer reads the language from the `<pre>` (and its `<code>`
descendant) in this **fixed precedence** order:

1. `data-ve-lang="<id>"` on the `<pre>`
2. `data-ve-lang="<id>"` on the `<code>` inside
3. `class="language-<id>"` or `class="lang-<id>"` on the `<pre>`
4. `class="language-<id>"` or `class="lang-<id>"` on the `<code>`
5. **`null`** → no highlighting (plain, byte-exact text)

Both `<pre>` AND `<code>` attributes are checked. Explicit attributes
beat class attributes. The first hit wins.

## A7.2 Why `null` is a deliberate result

"No language declared" means the reader did NOT ask for highlighting.
The tokenizer **never guesses a language from content** — an undeclared
block stays plain. This is the same discipline as "never decorate
something you weren't told to decorate" elsewhere in the runtime.

Auto-detection (content sniffing) is rejected for three reasons:
1. **Wrong-detection corrupts.** Detecting JS as Python because the
   line starts with `import` would colour every identifier wrong.
2. **The detector becomes the spec.** A hidden detector is a hidden
   contract that's impossible to debug.
3. **Author-knows-best.** The author always knows the language; making
   them say it costs ~12 characters per block and removes the only
   class of bug an auto-detector can introduce.

## A7.3 The two attribute conventions

Both are first-class:

| Convention | Example | When to use |
|---|---|---|
| `class="language-<id>"` | `<pre><code class="language-typescript">` | CommonMark / highlight.js / Prism convention. Authoritative for fenced code blocks rendered from Markdown. |
| `class="lang-<id>"` | `<pre><code class="lang-bash">` | Short alias also recognised by Prism. Lower friction in hand-authored HTML. |
| `data-ve-lang="<id>"` | `<pre data-ve-lang="diff">` | Plugin-native, escapes the class-string convention. Use when the `<pre>` is generated by a non-Markdown source (a JS template, a server-side render). |

A `<pre>` can carry BOTH `class="language-js"` AND
`data-ve-lang="diff"` — `data-ve-lang` wins (explicit beats class).

## A7.4 The 17-alias map (the full vocabulary)

The tokenizer ships seven canonical languages, plus 17 aliases that
resolve to one of them:

| Canonical | Aliases (all resolve to canonical) |
|---|---|
| `js` | `javascript`, `ts`, `typescript`, `jsx`, `tsx`, `mjs`, `cjs` |
| `python` | `py`, `python3` |
| `json` | `json5`, `jsonc` |
| `bash` | `sh`, `shell`, `zsh`, `console` |
| `html` | `xml`, `svg`, `htm` |
| `css` | `scss`, `less` |
| `diff` | `patch`, `udiff` |

**Total: 7 canonical + 17 aliases = 24 ids the tokenizer recognises.**

Case-insensitive — `data-ve-lang="TypeScript"` and `data-ve-lang="ts"`
both resolve to `js`.

Trimmed — `data-ve-lang=" js  "` resolves the same as `data-ve-lang="js"`.

## A7.5 The class-extraction regex

The class-form parser:

```js
function langFromClassName(className) {
  if (!className || typeof className !== 'string') return null;
  var classes = className.split(/\s+/);
  for (var i = 0; i < classes.length; i++) {
    var m = classes[i].match(/^(?:language|lang)-([\w+#.-]+)$/i);
    if (m) {
      var resolved = normalizeLang(m[1]);
      if (resolved) return resolved;
    }
  }
  return null;
}
```

The character class `[\w+#.-]+` accepts the languages Prism uses with
non-identifier characters in their id (`c++`, `c#`, etc.). The
tokenizer currently doesn't ship those languages, so they resolve to
`null` and the block stays plain — the regex is conservative; future
language additions will register without a parser change.

## A7.6 Why JS+TS share one table

TypeScript IS a JavaScript superset. The tokenizer's `js` table
includes both ES2024 keywords AND TS-specific ones (`abstract`,
`as`, `declare`, `enum`, `implements`, `interface`, `is`, `keyof`,
`namespace`, `private`, `protected`, `public`, `readonly`,
`satisfies`, `type`) so a `class="language-typescript"` block renders
correctly. The cost is that a `.ts`-specific identifier (`enum`) is
also coloured as a keyword in a plain `.js` block — which is fine: it
IS a reserved word in modern JS.

JSX/TSX share the same table because their syntax differences (the JSX
tags themselves) are handled by the HTML tag-aware sub-pass when the
`<` is encountered. The tokenizer does not yet ship a JSX-aware
sub-pass; JSX tag-runs render as plain text inside a JS-coloured
block, which is the correct fail-soft behaviour (probe passes,
identifiers stay readable, structure is just less coloured).

## A7.7 Unknown ids — the fail-soft path

If the author writes `class="language-rust"` (Rust not registered):

1. `langFromClassName` extracts `"rust"`.
2. `normalizeLang("rust")` returns `null` (no entry in the alias map).
3. `detectLanguage` returns `null`.
4. The integration with `initCodeGutter` calls
   `highlightBlock(lines, null)`.
5. `highlightBlock` with `null` returns `[escapeHtml(lines[0]),
   escapeHtml(lines[1]), …]` — every line is plain escaped text.
6. The gutter, copy button, selection, and wrap-marker all still work
   — the block is plain Rust but otherwise fully featured.

**This is the correct degradation.** Adding a new language is a
register-call in `amvcp-code-highlight.js`, not an author-side
override. Authors should never "fake" a language by mis-declaring it
to get some color — they get correctly-coloured-wrong-language and the
probe would reject it anyway.

## A7.8 Multi-class robustness

`<pre><code class="hljs language-typescript ve-code-block special">`
— the parser splits on whitespace and walks every class, taking the
first one that matches `^(?:language|lang)-([\w+#.-]+)$`. Order in the
class string doesn't matter.

A block with TWO `language-*` classes (a malformed input) returns the
first one in source order. The second is silently ignored.

## A7.9 Author rules

| Rule | Why |
|---|---|
| Declare the language on the `<code>`, not the `<pre>`, when authoring CommonMark-style HTML | Matches the convention every Markdown renderer emits — the `<code>` is where Markdown puts it. |
| Use `data-ve-lang` when the `<pre>` is in a template / scaffold | Lower friction, plugin-native, less likely to be stripped by an over-zealous HTML sanitiser. |
| Pick the canonical id when documenting, the alias when hand-authoring | `data-ve-lang="typescript"` for clarity in docs; `data-ve-lang="ts"` for terseness in templates. Both resolve identically. |
| Never declare a language you're not sure about — let it stay plain | A wrong language gets DISCARDED by the probe; the block ends up plain anyway. Save the noise. |
| Declare `diff` explicitly on diff blocks | The diff tokenizer is the simplest one (whole-line role); declaring `diff` gets you the color tints in the gutter. |

## A7.10 The future-proof shape

The alias map is the only thing the consumer sees. Adding a new
language is internal — `registerLanguage({ id, aliases, … })` extends
the map at module-load time; existing fixtures and authoring
conventions don't change. The plugin's current 7-language coverage is
deliberately tight (the languages an AI Maestro user actually
encounters) — a v2 might add Go / Rust / Swift / Lua but the contract
above is stable.

## A7.11 No tokens consumed (this reference)

Language resolution is a pure-JS feature with no theming surface.
Every visual-side behaviour reads from the token palette
([token-roles-palette.md](./token-roles-palette.md)) — this reference
only resolves WHICH palette role goes where.
