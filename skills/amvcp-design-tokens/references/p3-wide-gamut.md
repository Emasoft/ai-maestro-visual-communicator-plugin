# P3 wide-gamut accent token (DT-18)

CSS `@supports` progressive enhancement for P3 wide-gamut accents.
Fallback sRGB value always present; P3 version uses
`color(display-p3 r g b)` notation. Render the same accent at higher
saturation on P3 displays (Apple devices, recent iOS, recent macOS),
fall back to the perceptually-equivalent sRGB hex elsewhere.

## What it does

`generateOklchRamp(seedHex, steps, { p3: true })` attaches a parallel
`color(display-p3 r g b)` array as `ramp.p3`:

```js
var ramp = amvcpTokens.generateOklchRamp('#1d4ed8', 10, { p3: true });
// ramp:    ['#e8f1ff', '#d2e2fb', …, '#0a1d50']
// ramp.p3: ['color(display-p3 0.91 0.95 1.00)',
//           'color(display-p3 0.82 0.89 0.98)',
//           …,
//           'color(display-p3 0.04 0.11 0.31)']
```

The P3 variants are generated by `oklchToP3` (in `amvcp-tokens.js`,
not exported) — same OKLCh L/C/h, projected into P3 gamut for ~30%
higher chroma on capable displays.

## When to use

- Brand accents that benefit from a punchier rendering on Apple
  hardware (Apple TVs, MacBook Pro Liquid Retina XDR, iPhone Pro,
  iPad Pro);
- Marketing artifacts where the visual punch difference between sRGB
  and P3 is part of the brand experience;
- Test fixtures for color-management code (verify the @supports
  fallback chain works).

DON'T use for:

- documents that will primarily be read on non-P3 hardware
  (workstations with standard sRGB monitors) — the difference is
  invisible there;
- artifacts that must look IDENTICAL across all devices (the P3
  variant will look noticeably different on capable hardware);
- printed artifacts (CMYK printers don't render P3 anyway).

## Scaffold to emit

The pattern:

```html
<style>
  :root {
    /* Always-present sRGB fallback. */
    --vc-color-accent: #1d4ed8;
  }

  @supports (color: color(display-p3 0 0 0)) {
    :root {
      /* Punchier P3 variant on capable displays. */
      --vc-color-accent: color(display-p3 0.10 0.32 0.86);
    }
  }
</style>
```

Programmatic — emit both variants from one OKLCh call:

```js
var ramp = amvcpTokens.generateOklchRamp('#1d4ed8', 1, { p3: true });
var srgbHex = ramp[0];
var p3Color = ramp.p3[0];

var css =
  ':root { --vc-color-accent: ' + srgbHex + '; }\n' +
  '@supports (color: color(display-p3 0 0 0)) {\n' +
  '  :root { --vc-color-accent: ' + p3Color + '; }\n' +
  '}\n';
```

## Lib functions used

- `amvcpTokens.generateOklchRamp(seedHex, steps, { p3: true })` —
  returns the ramp + `.p3` sidecar
- (internal) `oklchToP3` — not exported; called by `generateOklchRamp`
  when `opts.p3` is set

## DESIGN.md tokens used

- writes (typical): `colors.<theme>.accent` (the sRGB hex) PLUS a
  per-page `<style>` block with the `@supports` fallback chain (NOT
  a DESIGN.md group — this is a CSS-side enhancement)
- emits: `--vc-color-accent` (the engine writes the sRGB hex; the
  `@supports` block conditionally overrides on P3 hardware)

## Anti-slop interaction

The P3 variant is a `color(display-p3 …)` value, not a hex — so the
slop gate's banned-hex check doesn't apply. The sRGB FALLBACK hex IS
checked, so a P3 accent whose sRGB fallback lands in the banned
indigo region will still flag — choose a different seed.

## Selection / comment / decision-mini contract

`--vc-selection-bg` is derived from `--vc-color-accent` via
`color-mix(in srgb, var(--vc-color-accent) 20%, transparent)`. When
the accent is `color(display-p3 …)`, the mix produces a P3 selection
mark on capable displays; on non-P3 it composes against the sRGB
fallback. Either way, selection composes correctly.

The focus ring (`--vc-focus-ring`) follows the same pattern (a 45%
mix). The role-map categorical ramps SHOULD NOT use P3 — they bake
to literal hex, so they're inherently sRGB; only the page accent
itself benefits from P3 enhancement.

## Visual verification

Per `skills/amvcp-self-debug-rules/SKILL.md` — open the artifact on
both a P3-capable display and a non-P3 display. Screenshot the accent
swatch in both. On the P3 display, the accent should look NOTICEABLY
more saturated (the wider gamut shows). On the non-P3 display, the
sRGB fallback hex shows — and the two screenshots should look
PERCEPTUALLY EQUIVALENT (the OKLCh source is the same, the projection
into each gamut is the perceptually-faithful mapping).

If only one display is available, emulate:

```js
await page.evaluate(() => {
  // Force the @supports block off:
  document.head.insertAdjacentHTML('beforeend',
    '<style>@supports (color: color(display-p3 0 0 0)) { :root { --vc-color-accent: var(--vc-color-accent-srgb-fallback) !important; } }</style>');
});
```

— this is an imperfect emulation; the only reliable way to test P3
is on actual P3 hardware.
